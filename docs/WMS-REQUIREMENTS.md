## 使用者目標與第一版提案

回答「哪個倉庫／儲位、哪項商品、有多少、為什麼增加或減少、誰在何時操作」。第一版以可追溯的實體庫存為目標。

提議依序交付：商品與倉庫主檔、庫存帳、入庫、出庫、庫存查詢與異動明細，再加入調撥及盤點調整。儲位及單位規格須先確認才定 schema。採購／銷售訂單、預留量、成本估價、會計、條碼硬體、批號效期、序號與外部匯入不自動納入第一張實作 Issue。

## 主檔與查詢

| 資源 | 必要資訊提案 | 規則提案 |
| --- | --- | --- |
| 商品 | 租戶、SKU、名稱、基本計量單位、啟用狀態 | SKU 在租戶內唯一；不同租戶可重複。已有異動後不能換 SKU 身分或基本單位；停用保留歷史 |
| 倉庫 | 租戶、代碼、名稱、啟用狀態 | 代碼租戶內唯一；有庫存或未結單據時不能停用，不能刪除歷史 |
| 儲位（若採用） | 租戶、倉庫、代碼、啟用狀態 | 代碼倉庫內唯一；跨倉儲位不可混用；是否提供預設收貨／出貨儲位待定 |
| 庫存餘額 | 商品、倉庫／儲位、現有量 | 只讀查詢，不允許 UI 直接覆寫；零庫存可篩選隱藏 |
| 異動帳 | 商品、來源單據、異動量、前後餘額、位置、操作者、過帳時間 | 不可修改／刪除；能按商品、位置、日期、單據類型篩選及分頁 |

重複 SKU／倉庫代碼的處理、名稱長度、條碼是否唯一與圖片／分類需求需在主檔 Issue 定稿。條碼可先視為可選查詢欄位，不假設連接掃描器或印標機。

## 單據流程與狀態

共同提案：`草稿 → 已過帳 → 已沖銷`；草稿也可取消。只有過帳影響庫存；編輯草稿不改庫存。過帳後不可修改數量、商品或位置，不直接刪除，錯誤透過有原始參照的反向單據處理。單號由 server 在租戶內產生，格式與重複策略於實作 Issue 定義。

### 入庫

1. 選擇收貨倉庫／儲位，填商品、正數數量及可選外部參考號／備註。
2. 儲存草稿，不增加庫存；確認時重新檢查商品及位置是否啟用。
3. 過帳一次性寫入入庫單、明細、正向異動、餘額與審計，成功後回傳單號及狀態。
4. 重複按下或網路重送不能重複加庫存。相同冪等鍵、相同內容回同一結果；相同鍵但內容不同拒絕。

供應商、採購單、驗收／退貨、分批到貨及收貨審批尚未核定，不自動增加完整採購模組。

### 出庫

1. 選出貨位置、商品與正數數量；顯示當下現有量，UI 的顯示不作授權或餘額依據。
2. 過帳在 DB 重新檢查餘額，提議拒絕負庫存。
3. 同交易寫出庫單、負向異動、餘額與審計。多品項任一不足時整張拒絕，不部分扣庫存。
4. 併發出庫與重送都不能造成超扣或重複扣帳；短缺訊息只顯示目前租戶可見資訊。

客戶、銷售單、揀貨／包裝／配送、需求預留及分批出貨尚未核定，不自動增加完整訂單模組。

### 調撥（接續提案）

即時調撥提案：同租戶來源位置扣庫存、目標位置加庫存，在同一交易完成，總量不變；來源不足則全數拒絕。不可跨租戶調撥。若實務需「出庫→在途→簽收」而非即時移轉，必須另定在途位置、差異、部分收貨、取消與責任歸屬，不把即時模式假裝成在途管理。

### 盤點與調整（接續提案）

盤點記錄系統量、實盤量、差異與原因；提議只有 Owner 能確認差異並過帳調整。不可直接把餘額欄位改成實盤量。盤點期間若仍可入出庫，需定義截點／凍結或版本衝突重盤機制，不能用過期系統量沖掉其他人的異動。初始庫存也使用有來源與原因的期初單，不直接寫餘額。

## 庫存不變條件提案

1. 每筆資料都有 tenant_id；商品、單據、位置、明細與帳之間用 tenant 複合外鍵保護。所有 API、列表、單筆及後續匯出都重新驗證 session、有效 membership 與租戶。
2. 已過帳的異動帳是追溯來源，餘額是同交易維護的彙總；應可重新加總核對。庫存只從已過帳異動改變。
3. 數量必須是正數入參，方向由單據類型決定；不接受客戶端提供任意正負量或前後餘額。
4. 不使用 JavaScript 浮點做庫存運算。整數採可驗證範圍的整數型別；若要小數／換算，再確定 Decimal 精度、最小單位與捨入規則。未確認前不建 quantity schema。
5. 原子過帳：單據狀態、異動帳、餘額與 metadata audit 同成功／同失敗；交易中鎖定相關餘額，鎖順序固定以降低死鎖，deadlock retry 需配合冪等鍵。
6. 外部請求及 UI 送出的 idempotency key 租戶內唯一，綁定操作者與請求內容；未完成交易、重播及不同內容的處理需測試。不信任只有前端禁用按鈕。
7. 已過帳記錄不可更新或實體刪除；沖銷要檢查原單、權限、未重複沖銷與反向餘額是否可成立。不能為沖銷偷偷允許負庫存。
8. metadata audit 記錄 actor、動作、單據／商品ID、時間與 request ID，避免把客戶資料、價格備註或 token 寫進日誌。業務明細與平台日誌分開保存。

## 權限矩陣提案

不新增跨租戶超級權限。Owner/Member 仍屬每個租戶的 membership，不能直接沿用 Project 的刪除規則當 WMS 過帳規則。

| 操作 | Owner 提案 | Member 提案 |
| --- | --- | --- |
| 查主檔、庫存、異動 | 可以 | 可以 |
| 商品／倉庫主檔維護 | 可以 | 暫不開放 |
| 建立／編輯入出庫草稿 | 可以 | 可以 |
| 正式過帳入出庫 | 可以 | 待確認：是否需倉管角色或主管審批 |
| 即時調撥 | 可以 | 待確認 |
| 盤點差異調整、期初、沖銷 | 可以，但需原因 | 暫不開放 |
| 成員及權限管理 | 沿用 M1 | 不可 |

倉庫專屬權限、審核人不得是建立者、唯讀／倉管／主管新角色等尚未核定。若需要，須先擴充授權模型與測試，不能只隱藏按鈕。

## 核心驗收案例

| 情境 | 預期結果提案 |
| --- | --- |
| A租戶與B租戶使用同一SKU代碼 | 各自獨立；A無法讀寫B的商品、單據、餘額或異動 |
| 草稿入庫10、尚未過帳 | 庫存不變 |
| 入庫10正式過帳，重送同一請求 | 庫存僅增加10，一份過帳來源；審計可追溯 |
| 餘額10，同時出庫7與7 | 只一張成功，另一張不足拒絕，最後餘額3 |
| 多品項出庫，其中一項不足 | 整張不過帳，各品項餘額及審計無部分成功 |
| A位置調撥4至B位置 | 同時A-4、B+4；任一失敗兩邊不變，租戶總量不變 |
| 已過帳單據嘗試直接改量／刪除 | 拒絕；改走有來源的沖銷／更正流程 |
| Member冒充Owner、跨租戶ID、停用後舊session | server拒絕，資料不變，不回其他租戶資訊 |
| 盤點保存後有新異動 | 依核定凍結／版本策略處理，不靜默覆蓋新異動 |
| 過帳時audit或餘額更新失敗 | 整體rollback，重送不重複扣加 |
| Decimal／單位換算（若納入） | 核定精度的精確結果，不出現浮點誤差或靜默捨入 |

每個實作 Issue 必須包含真實 PostgreSQL 約束、兩租戶授權、交易／併發／冪等測試，以及 HTTP 與關鍵瀏覽器操作結果。正式試用前重新排入 #8 的真人邀請驗收；不因 WMS 開發推進而自動標示成功。
